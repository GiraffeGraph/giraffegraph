# Isnad extraction evaluation kit

Scores extracted narrator mentions (isnad chains) against reference labels, prepares the sheets
human annotators need to produce those labels, and analyses and compares experiment runs. The
outputs of the runs made so far are listed under [Results](#results).

The matching criteria are part of the measurement protocol, so the kit is standalone: Python 3.12,
standard library only, nothing imported from `backend/`. Changing `scorer.py` changes the
measurement; do it deliberately and re-run the tests.

## Protocol

- **M1 strict**: normalised mention strings are equal.
- **M2 loose**: equal, or one contains the other, or content-token F1 >= 0.60.
- Mentions are aligned per hadith by maximum-weight bipartite matching. Equal-weight ties go to the
  matching with more pairs, then to the one that keeps chain order.
- Precision, recall, F1 and F0.5 are micro-averaged over hadiths. 95% intervals come from a
  percentile bootstrap that resamples hadiths.
- Exact-chain rate: share of hadiths where every mention is matched, in the same order, with no
  extras. Order concordance: mean share of matched pairs in agreeing order, over hadiths with at
  least two matches.

Normalisation removes diacritics and punctuation, unifies alef/ya/ta-marbuta/hamza forms, and
strips honorifics and a detached leading particle. It does not remove markup: strip any Sanadset
tags (`<NAR>`, `<IDF>`, ...) from mentions before writing them to JSONL.

## File formats

System output and reference are both JSONL, one hadith per line, mentions in chain order:

```json
{"hadith_id": "Nasai:693", "mentions": ["محمد بن منصور", "سفيان", "الزهري", "سعيد", "أبي هريرة"]}
```

`hadith_id` is `<collection>:<number>`. A reference hadith missing from the system file is scored
as zero system mentions. A system hadith missing from the reference is an error, as is a duplicate
id.

## Commands

Score a system:

```
python evaluation/scorer.py --system system.jsonl --reference reference.jsonl \
    [--bootstrap 2000] [--seed 0] [--out report.json]
```

Build the blind labelling sheet (hadith text only; tags removed, labels never read, rows shuffled
with a fixed seed). The generated `annotation/hadiths_to_label.tsv` holds the 50 pilot hadiths:

```
python evaluation/annotation/build_sheet.py <path/to/pilot_sample.json>
```

Convert a filled sheet to a reference, or compare two annotators (mutual F1 under M1 and M2, mean
`seconds_spent` per hadith):

```
python evaluation/annotation/to_reference.py filled.tsv --out reference.jsonl
python evaluation/annotation/to_reference.py annotator_a.tsv annotator_b.tsv
```

Annotators follow `annotation/GUIDELINE.md` (Turkish, v0 draft). In the `narrators` column mentions
are separated by ` | ` and parallel chains by ` || `; the reference keeps one ordered list per
hadith.

Tests:

```
uv run --no-project --python 3.12 --with pytest python -m pytest -q evaluation/tests
```

The pilot regression tests read `pilot_isnad.py` and `pilot_sample.json` from
`../../wiki/sources/claude-science-results` (override with `GIRAFFEGRAPH_PILOT_DIR`) and are skipped when the
files are absent. Add `--with numpy --with scipy` to also run the per-hadith comparison against the
pilot's own scorer. With the pilot files present and without numpy and scipy the result is 69 passed
and 1 skipped.

## Silver labels are not accuracy

Sanadset `<NAR>` labels (`ref_nars` in the pilot sample) are generated by regular expressions. A
score against them measures agreement with that regex output and is usable only to compare systems
with each other. Do not report it as accuracy. Accuracy claims need the human reference produced
with the annotation kit.

In `pilot_sample.json`, 17 of the 327 `ref_nars` mentions still contain a `<NAR>` or `<IDF>` tag.
Scored as saved, the pilot's rule parser gets M1 F1 0.595; with the tags stripped it gets the
pilot's reported 0.628. M2 F1 is 0.879 either way.

## Baseline run through the engine

`backend/scripts/run_isnad_baseline.py` sends hadiths through the real pipeline (isnad segmentation,
`rule_based_isnad` provider, validation, commit) on the in-memory backend and writes the system
output in the scorer's format. `evaluation/build_silver_reference.py` writes the reference file from
the same sample's rule-generated labels, with residual tags removed.

```
cd backend
uv run python scripts/run_isnad_baseline.py --input <hadiths.json> --out-dir <dir>
cd ..
python evaluation/build_silver_reference.py <hadiths.json> --out <dir>/reference_silver.jsonl
python evaluation/scorer.py --system <dir>/system_proposed.jsonl --reference <dir>/reference_silver.jsonl
```

`evaluation/results/2026-10-12-rule-based-baseline/` holds the output of this run on the 50-hadith
pilot sample. Its scores are agreement with rule-generated labels, not accuracy.

## Experiment runs through the engine

`backend/scripts/run_isnad_experiment.py` runs one extraction condition through the pipeline on the
in-memory backend (segmentation, extraction, validation, commit of every run with no open review
item) and exports it for analysis. No review decision is made in a run.

| `--condition` | Segmentation | Provider | Schema given to the model |
|---|---|---|---|
| `rule` | `isnad` | `rule_based_isnad` (no LLM) | n/a |
| `llm_schema_whole` | `paragraphs`, one call per hadith | `anthropic` | isnad schema reduced to its structure: no type or property descriptions, no extraction hints |
| `llm_isnad_whole` | `paragraphs`, one call per hadith | `anthropic` | isnad template schema with its hints |
| `llm_isnad_chain` | `isnad`, one call per chain | `anthropic` | isnad template schema with its hints |

```
cd backend
uv run python scripts/run_isnad_experiment.py --input <hadiths.json> --out-dir <dir> \
    --condition <name> [--model claude-haiku-5-5] [--effort low] [--limit N] \
    [--workers 4] [--max-cost-usd 1.00] [--cache-dir <dir>]
```

| Flag | Default | Meaning |
|---|---|---|
| `--input` | required | JSON list of objects with `coll`, `num` and `raw`. |
| `--out-dir` | required | Directory for the exports. |
| `--condition` | required | One of the four conditions above. |
| `--model` | `claude-haiku-5-5` | `claude-haiku-5-5` or `claude-sonnet-5-5`, the models the script has prices for. |
| `--effort` | `low` | `low`, `medium`, `high`, `xhigh` or `max`. |
| `--limit` | all | Only run the first N hadiths. |
| `--workers` | `4` | Concurrent provider calls. |
| `--max-cost-usd` | `1.00` | Spending limit. A call is issued only while the money spent, plus a worst-case reservation for every call in flight, stays within it. A hadith that needed a call that was not issued is left out of every export and listed in `hadith_ids_not_processed`. |
| `--cache-dir` | `backend/var/llm-cache` | On-disk response cache. A call with the same content is served from it at no cost in any later run. |

The LLM conditions need `ANTHROPIC_API_KEY`, read from the environment or the repository `.env`.
Cost is computed from the token counts of each response and the price table in the script (USD per
million tokens, as of 2026-10-06).

Output files in `--out-dir`:

| File | Content |
|---|---|
| `system_proposed.jsonl` | Narrator mentions of every proposed candidate, in the scorer's format. |
| `system_validated.jsonl` | Narrator mentions of the candidates validated without review. |
| `candidates.jsonl` | One row per candidate: type, name, properties, confidence, status, reason codes, evidence quotes. |
| `calls.jsonl` | One row per provider call: tokens, stop reason, latency, cost, error. |
| `run_report.json` | Counts of segments, calls, candidates by status and reason code, committed and blocked runs, graph size, tokens, cost, schema proposals, and a per-hadith list. |

## Analysing and comparing runs

`analyze_experiment.py` scores one run directory against a reference and writes `analysis.json` and
`analysis.md`: M1 and M2 scores of the proposed and of the validated output with bootstrap
intervals, the gate table, the AUC of the model's confidence for correct against wrong mentions,
the review workload and the cost. In the gate table every proposed narrator mention is correct
(matched to a reference mention under M2) or wrong (unmatched), and a mention is flagged by a reason
code when that code fired on its candidate node.

```
python evaluation/analyze_experiment.py --run <out-dir> --reference reference.jsonl \
    [--bootstrap 2000] [--seed 0] --out <dir>
```

`compare_runs.py` writes one Markdown file: a row per run, and paired bootstrap differences in M2
precision, recall and F1 between runs. A paired difference uses the hadiths both runs processed, and
every resample draws the same hadiths for both runs. Without `--pair`, every pair of runs is
compared.

```
python evaluation/compare_runs.py --runs <dir> <dir> ... --reference reference.jsonl \
    --out comparison.md [--pair <name> <name>]... [--bootstrap 2000] [--seed 0]
```

## Narrator identity baseline

`identity_baseline.py` reads a reference file with a narrator id per mention (`chains` and
`narrator_ids` per hadith) and reports what happens when mentions are grouped by a string key
instead of by the id: how many keys cover more than one person, how many people are split over
several keys, and pairwise and B-cubed precision and recall of the grouping. It reports two keys:
the exact written name and the scorer's normalised name. Mentions with a placeholder id are skipped.

```
python evaluation/identity_baseline.py --reference-chains reference_chains.jsonl [--out report.json]
```

## Results

Every score in these folders is agreement with a label set: Sanadset labels are generated by rules,
and Ifta labels are the markup of the Ifta' Sunnah platform as restructured by a third party. None
is a human gold standard, and no human reviewed any run. The reference files are built outside this
repository; in the project workspace they are under `data/eval/` and described in `data/README.md`.

| Folder | Content |
|---|---|
| `results/2026-10-12-rule-based-baseline/` | `run_isnad_baseline.py` on the 50 pilot hadiths, scored against Sanadset labels. |
| `results/2026-10-12-pilot50/` | The four conditions (Claude Haiku 5.5, effort `low`) on the 50 pilot hadiths against Sanadset labels; `compare-sanadset.md`. The rule-based segmenter was tuned on these hadiths. |
| `results/2026-10-12-sixbooks300/` | The four conditions (Claude Haiku 5.5, effort `low`) on 300 hadiths, 50 from each of the six canonical collections and none of them a pilot hadith, against Ifta labels; `compare-ifta.md`, `extra-tables-ifta.json` (by collection, chain count and number of reference mentions) and `subset36.json`. |
| `results/2026-10-12-subset36/` | The first six hadiths of each collection in that set: Claude Sonnet 5.5 at effort `low` in the two whole-hadith conditions, with the Haiku and rule runs on the same 36; `compare-ifta.md`. The Sonnet runs record a failure of the provider's wire format at this effort setting, not a model comparison. |
| `results/2026-10-12-identity-baseline/` | `identity_baseline.py` on the reference chains of the 300 hadiths; `sixbooks300.json`. |

In the `pilot50`, `sixbooks300` and `subset36` folders each run has its own folder with the five
export files and an `analysis-<reference>/` folder holding `analysis.json` and `analysis.md`.

## Supplementary tables

`extra_tables.py --runs <run-dir> ... --reference <reference.jsonl> [--reference-chains <file>] --out <file.json>`
writes, per run: loose-matching scores by collection, by number of reference chains and by number of
reference mentions; the score of the committed output only (a hadith whose run is blocked counts as
empty); the number of unmatched mentions a confidence threshold would send to review at each
threshold, beside the same count for the value-in-quotation check; and the number of provider calls
per hadith.

`classify_value_flags.py --run <run-dir> --hadiths <hadiths.json> --reference <reference.jsonl> --out <file.json>`
classifies every Narrator candidate that the value-in-quotation check flagged by the kind of change
(Latin transliteration, kinship reference replaced by a name, grammatical case, other) and reports
which unmatched mentions name the Prophet or have a name that does not occur in the text. The class
definitions are in the module docstring and in the output file.
